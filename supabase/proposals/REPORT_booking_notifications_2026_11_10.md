# Booking notifications, cancellation / rescheduling, and the switch-OFF question (10 Nov 2026) — LOCAL; nothing applied to Production

## 1. Client booking confirmation e-mail
- **Trigger:** only a successful booking *confirmation* (`confirmOrdinaryBooking`, after the database accepted it). A payment, a payment verification, a stage edit, a booking change and a cancellation cannot reach it (static guard tests; the database trigger creates notification records for a confirmation row and nothing else).
- **Content:** booking reference (the enquiry reference, e.g. ENQ-JRN-GHP; there is no separate booking number in the system and I did not invent one), service, every session's date and time in the booking's own time zone with its name and offset (e.g. "Thursday, 17 December 2026, 14:00–15:00 (Africa/Accra, GMT)", Qatar "…(Asia/Qatar, GMT+3)"), the arrangement (on site / studio / online, with the place or platform, session notes), the quotation reference, a link to the portal's Booking Details tab, and the studio contact (support@ordiftstudios.com, the same contact the payment receipt gives; no phone number is invented). It never shows money, the assigned person, agreements or internal notes. Free text is escaped.
- **Once:** the database creates one job per (confirmation, audience) with a UNIQUE key and claims it atomically (pending → processing), so a double click, a replay or two simultaneous requests cannot send it twice. A sent job can never change (guard trigger) and is never deleted.
- **Retry and audit:** the shared sender already retries transient provider errors (3 tries with back-off). Beyond that a failure is a visible row (status, error, tries, time). A Super Admin presses **Retry** (or **Send now** if it never started); the database claims failed / skipped / stale-processing jobs only (a job stuck after a crash is recoverable after 2 minutes; a fresh in-flight one is not stolen). An internal retry only addresses recipients not yet reached. No scheduler was added (same staff-triggered pattern as the payment receipt outbox, migrations 0030/0032). Every outcome also writes an `activity_log` row (`booking.notification_recorded` / `booking.notification_failed`, with audience, attempt, whether it was a retry). The exact subject and plain-text body are stored on the job and shown in the Booking card ("View the message"), so you can see what was or would be sent.
- **Not sent in these cases (recorded as `skipped`, message kept for staff):** the enquiry was recorded by staff (the established policy suppresses client e-mails for those: staff tell the client themselves, and can copy the message from the card), or the client has no e-mail address (placeholder).
- **Lab:** the lab sends nothing: `FORMS_SENDING_ENABLED` is not true and no mail provider key exists, so the shared sender only logs ("test mode"). The job records `provider_result = logged`, and the card says "Test mode: logged only, nothing was sent".

## 2. Internal "New Booking Confirmed"
Subject "New Booking Confirmed — <reference>". Reference, client, service, quotation, assigned personnel (member number first, per the Audit Identity Standard), each session in local time and UTC with its arrangement and notes, payment condition, verified paid and outstanding, agreement required / reference, who confirmed, and "re-confirmed after an earlier cancellation" where applicable, plus the admin link. It reuses the existing recipient rule (every active Super Admin plus Admins opted in to new-booking alerts), the shared dispatcher, one message per recipient, and the same once-only / retry / audit machinery. The old payment-time "New booking" notice remains only for the legacy switch-off behaviour.

## 3. Cancellation and rescheduling
- **Records:** the accepted quotation and every payment are never read or written by a cancellation or change (proved in the database rehearsal; the lab walk cancelled a paid booking: USD 400 still paid). A cancellation / change is a new append-only version; the project returns from Booked to Quotation Sent on cancellation (existing status model, no new status).
- **Display:** "Booking Cancelled — Rescheduling Pending" (derived, whatever has been paid) on the client dashboard and project header, a notice on the client's Booking Details tab (which never shows the old date as if it stood), the staff enquiry page and the Booking card. While a booking stands, the client's Booking Details tab shows the current confirmed schedule (so a reschedule is visible there at once).
- **Audit:** `booking.cancelled` / `booking.changed` / `enquiry.stage_change` (reason booking_cancelled), each with the Super Admin and the version.
- **Gap you should decide on (the lab walk shows it):** after a **reschedule** the client still holds the earlier "Booking Confirmed" e-mail with the OLD date, and after a **cancellation** nothing tells them. Today staff are told on screen to tell the client themselves. **Recommendation: yes, two separate client notices** (a reschedule is not a cancellation; the client must be told "now confirmed on the new details" vs "no longer confirmed"), sent from the same outbox (one more job kind, same once-only and retry), ideally after a prompt to the Super Admin ("Notify the client?", default yes), not silently, because staff sometimes phone first. Proposed wording (built and tested so it cannot say the wrong thing, but wired to nothing):

  **Cancellation** — subject "Booking cancelled — ENQ-JRN-GHP"
  > Hello Ama,
  > Your Photography booking (reference ENQ-JRN-GHP) for Thursday, 17 December 2026, 14:00–15:00 (Africa/Accra, GMT) has been cancelled. It is no longer confirmed, so please do not plan on that date.
  > We will contact you to agree a new date. Your accepted quotation and any payment you have made are unchanged and remain on your project; nothing is lost.
  > If you have questions, contact support@ordiftstudios.com quoting ENQ-JRN-GHP.

  **Reschedule** — subject "Booking updated — ENQ-JRN-GHP"
  > Hello Ama,
  > The date or arrangements for your Photography booking (reference ENQ-JRN-GHP) have changed.
  > Previously: Thursday, 17 December 2026, 14:00–15:00 (Africa/Accra, GMT)
  > Now confirmed: Friday 18 December 2026, 09:00–10:00 (Africa/Accra, GMT)
  > Arrangement: At the studio — Synthetic studio, Accra
  > Your booking remains confirmed on the new details above. If they do not suit you, contact support@ordiftstudios.com quoting ENQ-JRN-GHP.

  Deliberately silent on refunds (a separate decision). Say if you want different wording, a different contact line, or sending without a prompt.

## 4. The switch-OFF question (Production today)
**Finding: yes.** With `BOOKING_CONFIRMATION_ENABLED` off (Production), `advanceStageOnFullPayment` is unchanged and unconditional: when an ordinary enquiry's completed payments reach its amount due it is moved to "booked", the client is e-mailed "Booking Confirmed" and the team gets "New Booking". Production has no booking tables, so by definition no booking record exists for that "booked". Seen live in the lab on 9 Nov (ENQ-JRN-GHY: stage_change by system + both e-mails, no booking). Consequences in Production: a fully paid enquiry is called booked and the client told "Booking Confirmed" with no date, no availability / conflict / leave check, no person assigned; and when booking confirmation is later switched on, every such legacy row reads "Booked (no booking record)" to staff.
Also found: `summarizeEntityPayments` calls an enquiry Paid when the net completed payments are > 0 and `>= amount_due`, and an UNSET amount due counts as 0, so any completed payment on an enquiry with no amount due also reads Paid (and, switch off, books it). Checkout requires an amount due, so this needs a manual / admin payment; characterised by an existing test; not changed (it is payment-status semantics).
Manual stage change to "booked" stays available with the switch off (it sends no e-mail), and Crew Support is excluded in both states.
**Compatibility-safe correction (implemented but INERT by default):** a separate environment variable `PAYMENT_AUTO_BOOKS_ENQUIRY`. Only the exact word `false` changes anything (a typo cannot), so shipping the code changes nothing in Production. With it set to `false` and the switch still off: a payment is recorded, the stage does not move, no "Booking Confirmed" / "New booking" e-mail is produced, the project shows "Paid — scheduling pending" / "Payment received — scheduling pending" (derived; no booking tables read), and staff move the stage to Booked by hand once scheduled (existing control, unchanged). A project staff set to Booked by hand is not flagged as an anomaly in this mode. Tested in all four states (switch on/off × variable): only "switch off and variable not false" books from a payment; Crew Support never; switch on wins.
**Needs your decision before anyone sets it in Production:** with the variable false and the switch off, clients get no booking e-mail at all (only the payment receipt) until booking confirmation is switched on. Options: (a) accept that, staff telling clients; (b) switch on booking confirmation (its e-mail then applies); (c) a later change to let the manual Booked move send the legacy e-mail. Existing "booked" legacy rows are not touched by any of this; run `DIAGNOSTIC_booked_without_booking_record.sql` first when you decide.

## 5. Migration proposal and rollback
- `PROPOSAL_booking_notifications.sql` (needs PROPOSAL_booking_confirmation.sql; additive: one table, one guard trigger, one trigger on confirmations, two server-only functions; no existing row, table or function changed; refuses to run if the booking tables are absent). Rollback `ROLLBACK_booking_notifications.sql` (drops the table: export the delivery history first). Applied to the LAB only (kit `apply_booking_notifications_to_lab.sh` / `rollback_...`). Confirmations made before it have no notification records (never notified; nothing back-filled).
- After applying a migration to a Supabase API, reload its schema cache; in the lab the first confirmation after applying found the new functions "not in the cache", so its two jobs stayed **pending** and the panel offered "Send now" (a useful proof the failure is visible and recoverable). The code treats "function missing" as a quiet no-op so Production (tables absent) is unaffected.
- Order for Production (each needs your separate approval; none requested): confirmation proposal, cancel-stage proposal, notifications proposal, then the application release, then (separately) the switch.

## 7. Remaining issues and decisions
1. **Client notices for reschedule / cancellation** (section 3): approve or change the wording, and say prompt vs automatic.
2. Staff-recorded enquiries (WhatsApp, phone, in person) are never e-mailed (existing policy): staff copy the message from the card. Confirm that is still what you want for booking confirmations.
3. Switch-OFF opt-out `PAYMENT_AUTO_BOOKS_ENQUIRY=false` and what clients receive meanwhile (section 4).
4. "Booking reference" = the enquiry reference. A distinct booking number would be a separate design.
5. The assigned person is not an internal recipient (the existing recipient rule is Super Admins plus opted-in Admins). Adding them is a product decision.
6. Retry is manual (a Super Admin must press it); a failed message waits visibly. An automatic sweep would be a scheduler, which you deferred.
7. After any migration on a Supabase API, reload the schema cache (see section 5).
