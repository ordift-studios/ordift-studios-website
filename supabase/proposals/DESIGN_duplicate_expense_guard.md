# Duplicate-expense guard — review and recommendation (LOCAL, 2026-11-10; nothing applied)

**Risk:** the same cost counted twice — once as an equipment acquisition (migration 0186, live) and once as an expense line in the existing expense form (`entity_expenses`).
**Gap found:** the expense form already refuses a repeated receipt, a repeated stored document (including byte-identical copies, other versions and other classes) and a repeated request reference — but only against OTHER EXPENSES. It never looked at acquisitions, and the acquisition path never looked at expenses. The earlier trigger proposal only matched number + supplier in one direction.
**Recommended implementation (two layers, safest first):**
1. **Application check — no migration, read-only, friendly messages (built, tested):** `src/lib/organization/financeOverlap.ts`, called inside `recordEntityReceipt` and `recordEquipmentAcquisition` before anything is written. Refuses when the same invoice (number AND supplier, case/space-insensitive) or the same stored document family (the file, its byte-identical copies, its earlier version) backs both. Covers the acquisition's invoice, statement evidence, financing confirmation and instalment evidence. Ships with a normal code deployment; no database change, so it cannot lock or break a live table.
2. **Database triggers — optional defence in depth (v2 prepared and rehearsed, not applied):** `PROPOSAL_optional_duplicate_expense_guard.sql` (+rollback): two before-insert triggers, both directions, exact rules only (same document row, or same number AND supplier). No existing row, column, constraint or trigger changes; rollback drops them. Rehearsal: apply PASS, rollback PASS, self-test fails as designed; covers refusing in both directions and leaving unrelated expenses, the same number at another entity and the same supplier with another number alone.
**Why not the trigger alone:** it cannot see byte-identical copies (a different row), it changes the behaviour of a live table, and its error text is less helpful. **Why not the application alone:** a write that bypasses the application would not be stopped. Recommendation: ship layer 1 with the next code release; apply layer 2 only after the FNAC record is in (so a legitimate record is never blocked mid-entry) and with its own backup + approval, or not at all if layer 1 suffices.
**Known limits:** a differently spelled supplier or invoice number (for example "FNAC" vs "FNAC Qatar") is not caught by number+supplier — the document rule still catches the same file; this remains a procedure point (never key the same purchase twice). A false refusal is fixed by voiding or correcting the entry.
