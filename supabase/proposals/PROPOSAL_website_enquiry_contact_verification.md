# PROPOSAL (not built): verifying a website-form e-mail address without full portal registration — 10 Nov 2026

## The problem
A website enquiry stores whatever address the visitor typed. Typing an address proves nothing about who controls it, so booking details (date, place) must not be e-mailed to it. Today (built, tested): a website-form enquiry with no verified portal owner receives NO booking notices by e-mail; staff tell the client and record it, and the ordinary enquiry acknowledgement and quotation e-mails are unchanged. Clients who sign in to the portal (the project links to a confirmed sign-in) are covered: their confirmed account address is used. The proposal below is for the client who does not want an account.

## Recommended mechanism: a one-time "confirm this is my e-mail" link (no account, no password)
1. **Trigger.** When a booking notice cannot be sent because the address is unverified, the Notifications box offers staff **"Send a verification link"**. (Optionally the enquiry acknowledgement could carry the same link from day one; that is a separate decision because it changes an existing e-mail.)
2. **What is sent.** A short message to the typed address that contains NO booking details: "Please confirm this is your e-mail address so we can send you your booking details. Confirm: <link>. If you did not make this enquiry, ignore this message." The link holds a 256-bit random token; only its SHA-256 hash is stored (the same hash-only pattern as the portal claim process).
3. **Proof.** Opening the link and pressing **Confirm** proves control of the mailbox at that moment (the page shows only the reference and a Confirm button; it never shows booking details before the proof). A bot or mail scanner that merely fetches the link cannot confirm: the POST needs the button press.
4. **Effect.** The enquiry records `contact_email_verified_at` and the address it applies to. From then on booking notices go to THAT address (verified), exactly as to an account address. If staff later change the enquiry's e-mail, the verification does not carry over. Verification never grants portal access to the project (that stays the separate link-and-code claim); it only licenses e-mail.
5. **Limits and safeguards.** Single use; expires in 7 days; at most 3 sends per enquiry per day and 5 per week; a new link voids the old one; every send and confirmation is audited with who/when/channel; the token is never logged or shown after creation; a shared mailbox can confirm (the proof is control of the mailbox, not identity), so the staff card keeps the existing "shared mailbox" warning and the portal link-and-code claim remains the strongest route. Confirmed addresses are never used for anything beyond booking notices without a separate decision.
6. **Why this and not the alternatives.** (a) *Require full portal registration*: strongest, but forces an account on clients who only want a date by e-mail. (b) *Send details to the typed address anyway*: the risk this work removes. (c) *Phone-only delivery*: works today (manual record) but does not scale. (d) *A 6-digit code instead of a link*: needs a second channel to deliver it; the link is simpler and equally strong for mailbox control.

## What it would need (nothing here is built or applied)
- One migration: table `enquiry_contact_verifications` (enquiry_id, email snapshot, token_hash unique, created_by, created_at, expires_at, confirmed_at, voided_at; RLS on, no direct grants) plus two server-only functions (`create_contact_verification`, `confirm_contact_verification`) and one nullable column pair on `enquiries` (or a view over the table: the table alone is enough, "verified" = a confirmed, unvoided row whose email equals the current enquiry email).
- App: a public confirm page (`/verify-contact/<token>`, no sign-in, POST to confirm, generic messages that never reveal whose project it is), a staff action with the rate limits, the address rule gaining one branch (verified address -> send), tests and a rehearsal, and a one-line change to the Notifications card.
- Rollback: drop the table and functions; the address rule returns to "no verified owner -> no e-mail".
- Effort: about the size of the portal claim feature (a day or two of build and verification). **Needs your approval before any build.**
