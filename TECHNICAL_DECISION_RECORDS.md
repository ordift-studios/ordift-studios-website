# Technical Decision Records (TDR)

**Established:** 2026-07-30, superseding `ARCHITECTURE_DECISIONS.md` at your explicit request, as part of Version 1.0.5 — Platform Foundation Hardening.

**Why this replaces, rather than sits alongside, the earlier ADR log:** running two parallel decision-record systems with different formats would itself be exactly the kind of documentation drift a platform meant to last 10-20 years shouldn't accumulate — the same reasoning already applied once before in this project (`DOCUMENTATION_INDEX.md` §3, retiring `VERSIONS.md`'s old roadmap table rather than maintaining two). `ARCHITECTURE_DECISIONS.md`'s 8 entries are migrated below under the TDR numbering and the richer field set you specified; that file now only points here.

**Format:**

```
### TDR-NNN — Title
- Status: Accepted / Superseded / Under Review
- Context: the situation/background this decision was made within
- Problem: the specific question that needed answering
- Options Considered: every option genuinely evaluated
- Decision Made: what was chosen
- Reasoning: why
- Consequences: trade-offs accepted, what this enables/constrains
- Alternatives Rejected: each non-chosen option, with the specific reason it lost
- Related Files: code/docs this decision touches
- Review Date: a condition or point that should trigger revisiting this decision (a fixed calendar date only where one genuinely applies — most engineering decisions are better tied to a triggering condition than an arbitrary date)
```

Every new major engineering decision going forward gets a new TDR here at decision time — cross-referenced from `TECHNICAL_DEBT_REGISTER.md` where it produces an accepted trade-off, and from `MILESTONES.md` at the point it ships.

### TDR-001 — CMS-agnostic content repository abstraction
- **Status:** Accepted, implemented
- **Context:** the site initially read content from local TypeScript fixture files during early development, before a real CMS was connected.
- **Problem:** moving to Sanity meant every page component would otherwise need to call Sanity's specific query/client API directly, coupling every page to one vendor.
- **Options Considered:** (1) call the Sanity client directly from every page/component; (2) build a `contentRepository` interface with swappable implementations.
- **Decision Made:** built the `contentRepository` abstraction (`src/lib/content/index.ts`) with `sanityContentRepository` as the live implementation.
- **Reasoning:** decouples every consuming page from the specific CMS vendor; made the CMS migration itself stageable (swap the implementation behind one flag) instead of a site-wide rewrite; every content type added since (Ordift Pulse, media metadata, site-wide singletons) shipped through the same seam without touching page components.
- **Consequences:** one extra abstraction layer to maintain in exchange for migration safety and a single seam for every future content type.
- **Alternatives Rejected:** direct Sanity calls per page — rejected because it would make any future CMS change (or even a Sanity API version bump with breaking query changes) a site-wide, high-risk rewrite instead of a one-file change.
- **Related Files:** `src/lib/content/index.ts`, `src/lib/content/sanity/`, `CMS_MIGRATION.md`.
- **Review Date:** only if a second CMS implementation is ever genuinely needed (not anticipated).

### TDR-002 — Supabase Row-Level Security as the primary authorization boundary
- **Status:** Accepted, implemented
- **Context:** the platform has seven distinct roles (Super Admin/Admin/Staff/Contractor/Vendor/Model/Client), each needing different data visibility across a growing number of tables.
- **Problem:** where should the actual security boundary live — in application code, in the database, or both?
- **Options Considered:** (1) application-layer-only checks (API routes/server components check role before returning data); (2) Postgres RLS as the real boundary, app code as a secondary convenience layer.
- **Decision Made:** RLS policies are the actual security boundary — a query only returns rows a given authenticated user is permitted to see, regardless of what the calling code does.
- **Reasoning:** application-layer-only checks fail silently the moment one code path forgets to check; RLS makes an unauthorized read structurally impossible instead of a discipline requirement.
- **Consequences:** RLS policy correctness is the single most security-critical thing in the schema; every new table needs its policy designed deliberately and its `service_role` grants scoped exactly (the lesson from migrations 0010-0012, where over-broad grants were caught and narrowed).
- **Alternatives Rejected:** app-layer-only authorization — rejected because it was already a known, well-documented bug class (one missed check anywhere = a real breach), and this project explicitly wanted a guarantee, not a discipline.
- **Related Files:** every RLS policy across `supabase/migrations/`, `src/lib/portal/roles.ts`, `src/lib/portal/rls.integration.test.ts` (the Version 1.0.5 integration test proving this decision holds in practice).
- **Review Date:** every new table addition (Version 1.1 onward) must have its RLS policy reviewed before merge; also the subject of Version 1.0.5 Workstream I's security re-review.

### TDR-003 — Google Sheets as a secondary durability layer, Supabase as primary
- **Status:** Accepted, implemented
- **Context:** business operations wanted enquiry/booking/registration data visible in Google Sheets — a familiar tool for non-technical staff.
- **Problem:** a third-party API can't safely be the primary system of record (it can fail, rate-limit, or have an outage independent of the platform) — how to give the business its Sheets workflow without making platform correctness depend on it?
- **Options Considered:** (1) Google Sheets as the sole/primary store; (2) Supabase primary with Sheets as a best-effort mirror; (3) Supabase only, no Sheets integration at all.
- **Decision Made:** Supabase Postgres is the system of record; every write also attempts a Sheets sync, and a failed sync is logged to `sheet_sync_failures` (migration 0013) rather than blocking or losing the primary submission.
- **Reasoning:** gives the business what it wants without coupling platform correctness to a third-party API's uptime; the dead-letter table makes a Sheets outage recoverable instead of silent data loss.
- **Consequences:** dual-write complexity; the dead-letter table needs monitoring to be useful, which it currently doesn't have (TD-005) — an operational gap in an otherwise sound decision.
- **Alternatives Rejected:** Sheets-as-primary — rejected outright, unacceptable reliability profile for a system of record; Supabase-only (no Sheets) — rejected because it would have ignored a genuine, named business requirement for a tool staff already knew how to use.
- **Related Files:** `supabase/migrations/0013_record_ids_and_sheet_sync.sql`, `src/lib/shared/sheetSyncFailures.ts`, `GOOGLE_SHEETS_INTEGRATION.md`.
- **Review Date:** if Sheets sync failure rate ever becomes chronic rather than occasional — reassess live-sync vs. scheduled batch export.

### TDR-004 — Four independent axes for people-classification: Role, Position, Grade, Engagement Type
- **Status:** Accepted, implemented
- **Context:** the platform needed to represent organizational seniority (Grade) and job function (Position) alongside permission-role (Role) and contractual relationship (Engagement Type).
- **Problem:** how to add seniority/title concepts without ever letting them accidentally gate access?
- **Options Considered:** (1) fold seniority/title into the existing Role enum; (2) keep four genuinely independent concepts, each its own table/column, none referenced by permission checks except Role.
- **Decision Made:** four independent axes, hard constraint that Grade/Position/Engagement Type are never read by an authorization check.
- **Reasoning:** conflating "what you're allowed to do" with "how senior you are" or "what you're called" is a known source of permission bugs; structural separation makes that bug class impossible rather than a code-review discipline.
- **Consequences:** more tables/lookups than a single combined field; in exchange Grade stays confidential (admin-only) while Role/permissions stay functionally necessary everywhere, fully independent of each other.
- **Alternatives Rejected:** folding Grade/Position into Role — rejected because it directly risked a senior title accidentally granting access, or a permission change accidentally affecting org-chart position.
- **Related Files:** `supabase/migrations/0017_grades.sql`, `supabase/migrations/0019_classifications.sql`, `ADMIN_GUIDE.md` §9.1.
- **Review Date:** any future feature that wants to "just check someone's Grade to decide access" is a signal this boundary is under pressure — treat as a design smell, not a precedent.

### TDR-005 — Separate Sanity datasets for staging and production
- **Status:** Accepted, implemented
- **Context:** needed to test real CMS-driven pages with placeholder/sample content with zero risk of that content reaching production.
- **Problem:** how to guarantee staging sample content structurally cannot appear on the live site?
- **Options Considered:** (1) one shared dataset with a `status`/`environment` flag on documents; (2) two fully separate Sanity datasets, production querying only its own.
- **Decision Made:** fully separate datasets.
- **Reasoning:** a content-flag approach depends on every query correctly filtering, forever — one missed filter leaks sample content to production. Dataset separation makes that failure mode structurally impossible, same reasoning as TDR-002.
- **Consequences:** content approved for production must be explicitly loaded into the production dataset (no promote-by-flag); more manual step, but it enforces the project's "never invent facts, always get explicit approval" content discipline at the infrastructure level.
- **Alternatives Rejected:** shared-dataset-with-flag — rejected because its safety depended on perfect, permanent query discipline rather than a structural guarantee.
- **Related Files:** `STAGING.md`, `sanity.config.ts`, `.env.example` (`NEXT_PUBLIC_SANITY_DATASET`).
- **Review Date:** none scheduled — this pattern is the default for any future environment-separation need (e.g. a second business unit onboarding onto the `business_id`-scoped schema).

- **Consequences:** the one deliberate "build ahead of immediate need" in the codebase, justified by already-demonstrated repetition rather than guessed future need.
- **Alternatives Rejected:** per-content-type implementations — rejected because the pattern was already proven identical, making duplication pure waste, not risk-avoidance.

### TDR-007 — Ordift Pulse embedded into existing Journal section, not a separate route
- **Status:** Accepted, implemented
- **Context:** Ordift Pulse (curated industry-news feed) was built well ahead of its originally planned schedule (Version 4.0).
- **Problem:** give Pulse a public-facing surface without building a second, largely-duplicate article system alongside the existing Journal.
- **Options Considered:** (1) a dedicated `/pulse` route and UI, fully separate from `/journal`; (2) embed Pulse into `/journal` via a Content Type filter and trust badges, keeping the underlying schemas (`journalPost` vs `pulseArticle`) fully separate.
- **Decision Made:** embedded into `/journal`, schemas kept separate.
- **Reasoning:** the public-facing cost of a second content hub (navigation, discovery, duplicate templates) wasn't justified by demonstrated audience demand yet; keeping schemas separate preserved the option to split later without a data migration.
- **Consequences:** `/journal` now serves two conceptually distinct content types behind one UI — slightly more complex hub logic, zero duplicate infrastructure.
- **Alternatives Rejected:** dedicated `/pulse` route now — rejected as premature investment in discovery/navigation infrastructure for content whose audience demand hadn't been demonstrated yet.
- **Related Files:** `PULSE_ARCHITECTURE.md`, `STORIES_PULSE_INTEGRATION.md`, `src/lib/content/storiesFeed.ts`.
- **Review Date:** revisit if audience demand for a distinct Pulse identity ever justifies the split (explicitly flagged in `PRODUCT_ROADMAP.md` Version 4.0).

### TDR-008 — Forms default to external reference links, not direct upload (Tier 1 vs. Tier 2)
- **Status:** Accepted, implemented (Tier 1); Tier 2 explicitly not yet implemented
- **Context:** several forms conceptually want to accept files (portfolio samples, booking references), but real file upload requires answering storage/access/retention questions not yet evaluated.
- **Problem:** ship low-sensitivity forms without either over-building for their needs or under-building security for the high-sensitivity forms that will come later.
- **Options Considered:** (1) build generic upload immediately for any form that could use it; (2) tier by data sensitivity — Tier 1 uses reference links only, Tier 2 (CVs, ID documents, consent forms) stays disabled until a dedicated secure-storage evaluation is complete.
- **Decision Made:** (2) — tiered, with Tier 2 explicitly gated.
- **Reasoning:** building upload infrastructure before deciding how sensitive documents will be stored risks either over-building for Tier 1 or under-building security for Tier 2.
- **Consequences:** Client Portal currently has zero upload capability by design (confirmed in-code); Version 2.0 (Talent Management) cannot ship Contracts/Documents until the secure-storage evaluation happens — already a hard release-criterion dependency in `PRODUCT_ROADMAP.md`.
- **Alternatives Rejected:** building generic upload now — rejected because it would have meant guessing a security posture for sensitive documents (CVs, ID) without a deliberate evaluation, the single highest legal/privacy risk item on the entire roadmap per `PRODUCT_ROADMAP.md` Version 2.0's own risk note.
- **Related Files:** `src/lib/admin/deliverables.ts`, `PRODUCT_ROADMAP.md` (Version 2.0 dependency).
- **Review Date:** Version 2.0's kickoff — the storage evaluation must happen as its own explicit decision point before any code touches real sensitive documents.

### TDR-009 — Platform Health Dashboard stays a documentation layer, not a live application, until named triggers are met
- **Status:** Accepted, implemented (documentation layer only)
- **Context:** Version 1.0.5 Workstream G originally named a "Platform Health Dashboard." At current scale — pre-launch, founder-led, no engineering team checking a dashboard daily — a live internal application is itself a new feature, which cuts directly against this milestone's purpose ("not another feature above the platform").
- **Problem:** how to give visibility into test/CI/deployment/monitoring/backup/security/debt/release status without building disproportionate infrastructure for the team size that exists today.
- **Options Considered:** (1) build a live, real-time internal dashboard application now; (2) a maintained `SYSTEM_HEALTH.md` documentation/evidence layer, consolidating or referencing facts already owned by other living documents, with no new infrastructure.
- **Decision Made:** (2) — `SYSTEM_HEALTH.md`, explicitly scoped as documentation/evidence, not a new build.
- **Reasoning:** confirmed 2026-07-30 — the maintenance cost of a live app (hosting, auth, upkeep) isn't justified when the person who'd check it is also the person maintaining the underlying documents it would summarize. A markdown layer gets most of the visibility value at near-zero ongoing cost.
- **Consequences:** `SYSTEM_HEALTH.md` can go stale if not updated as part of each milestone's definition-of-done — an accepted, actively mitigated trade-off, not an oversight.
- **Alternatives Rejected:** the live dashboard — not rejected permanently, deferred behind explicit, named reactivation triggers (below) rather than built speculatively.
- **Related Files:** `SYSTEM_HEALTH.md` (Workstream G), `PRODUCT_ROADMAP.md` Version 1.0.5 Workstream G, `PLATFORM_HEALTH_REVIEW.md`.
- **Review Date:** reconsider a live dashboard only when any of these becomes true — manual maintenance of `SYSTEM_HEALTH.md` becomes unreliable; multiple engineers or environments need centralized visibility; incident volume justifies it; real-time operational decisions start depending on it; or the cost of not automating demonstrably exceeds the cost of building and maintaining it. None of these are true as of 2026-07-30.

### TDR-010 — CI pipeline scoped to lint/typecheck/unit-tests/build; integration tests deliberately excluded for now
- **Status:** Accepted, implemented
- **Context:** Version 1.0.5 Workstream B needed a CI pipeline. The integration-test suite built in Workstream A runs against real staging Supabase/Sheets credentials (`INTEGRATION_TESTING_STRATEGY.md`), which would need to exist as GitHub Actions repository secrets to run in CI.
- **Problem:** whether to wire the full test suite (unit + integration) into CI immediately, or scope the first CI pass more narrowly.
- **Options Considered:** (1) wire everything, including integration tests, requiring staging secrets to be added to GitHub immediately; (2) scope CI to lint + typecheck + unit tests + build only, matching Workstream B's original description exactly, and treat wiring integration tests into CI as a distinct, later decision.
- **Decision Made:** (2). `.github/workflows/ci.yml` runs lint/typecheck/unit-tests unconditionally, plus a production build (which itself needs Sanity credentials for static-generated routes — see below), and does not run integration tests.
- **Reasoning:** adding real staging credentials to a third-party CI system (GitHub Actions) is a security-relevant decision this project's own standards require flagging for explicit approval, not bundling into a "build the CI pipeline" task. It's also more naturally sequenced after Workstream I (secrets-management policy) than before it.
- **Consequences:** CI provides real, immediate regression protection for logic/types/lint/build correctness starting now; integration-test protection in CI is a follow-up decision, not yet made. The `build` job needs `NEXT_PUBLIC_SANITY_PROJECT_ID`/`NEXT_PUBLIC_SANITY_DATASET`/`SANITY_API_VERSION`/`SANITY_API_TOKEN` set as GitHub repository secrets (Settings → Secrets and variables → Actions) — without them, the build job will fail or silently generate static routes with zero content, per `src/sanity/lib/client.ts`'s documented behavior (both Sanity datasets require a token even for reads). This is a manual step only you can do (no GitHub dashboard/secrets access from this environment) — flagged explicitly rather than worked around. **Verified 2026-07-30, real run `30570600185`:** quality-gates passed on first attempt; build initially failed on a malformed `NEXT_PUBLIC_SANITY_PROJECT_ID` secret value (real, diagnosed root cause — not a flake), corrected, re-run, passed. Logs independently checked for secret leakage (none) and unexpected warnings (none new). The connected Vercel deployment for the same push independently confirmed `Ready` on the production alias, with a live health check across `/`, `/coming-soon`, `/admin`, `/portal/login`, `/sitemap.xml`.
- **Alternatives Rejected:** wiring integration tests into CI now — rejected as premature given the credential-security question hasn't been deliberately decided yet.
- **Related Files:** `.github/workflows/ci.yml`, `INTEGRATION_TESTING_STRATEGY.md` §6, `src/sanity/lib/client.ts`.
- **Review Date:** once Workstream I (secrets-management policy) is complete, revisit whether/how integration tests join CI.

### TDR-011 — Enterprise Legal Series content lives in code (`src/lib/legal/`), not the Sanity `legalPage` type

- **Status:** Accepted, implemented
- **Context:** OS-LGL-001 (Privacy Policy) arrived approved and ready for integration 2026-08-04, the first document in a planned "Ordift Studios Enterprise Legal Series" meant to scale to Cookie Policy, Website Terms, Booking Terms, and eventually a broader enterprise documentation framework (client agreements, governance docs, policies). Requirements included: sticky/expandable table of contents anchored to every heading, a structured Document Control metadata block (code, version, status, classification, dates, owner, related documents), an inline definitions list, mixed prose/list/table content, and four downloadable publication formats (PDF/DOCX/HTML/MD) with letterhead branding. The existing `legalPage` Sanity type (used by `/legal/terms`, `/legal/cookies`, `/legal/booking`) is a single plain-text `body` field — already flagged as `TD-010` in `TECHNICAL_DEBT_REGISTER.md` precisely because it can't carry this kind of structure.
- **Problem:** whether to force this content into the existing Sanity `legalPage.body` string (parsing structure back out of markdown-like conventions at render time), migrate that Sanity schema to portable text immediately, or introduce a separate, structured content source for this document type specifically.
- **Options Considered:** (1) cram OS-LGL-001 into the existing plain-text `body` field, inferring section boundaries/lists/tables from text conventions at render time; (2) migrate `legalPage.body` to Sanity portable text now, affecting all four legal slugs at once; (3) a new, code-based structured content source (`src/lib/legal/`) specific to the Enterprise Legal Series, following this project's own established CMS-agnostic pattern (a domain-type layer + a registry, the same shape as `contentRepository`) — loaded via a registry that future documents (and a future CMS adapter) plug into without touching consumers.
- **Decision Made:** (3). `src/lib/legal/types.ts` defines the domain model (`LegalDocument`, `DocumentControlMetadata`, `LegalSection`, `LegalContentNode`, `DefinedTerm`); `src/lib/legal/documents/os-lgl-001-privacy.ts` holds OS-LGL-001's content verbatim; `src/lib/legal/registry.ts` is the single extension point future documents (Cookie Policy, Website Terms, Booking Terms) get added to. The `/legal/[slug]` route checks the registry first and falls through unchanged to the existing Sanity-backed renderer for any slug not yet registered — `cookies`/`terms`/`booking` are completely unaffected until their own approved documents arrive.
- **Reasoning:** Option (1) would have meant writing a markdown-like parser to reconstruct structure (heading levels, lists, tables, a definitions block) from a single string — fragile, and exactly the "silently force-fitting" TD-010 already warned against. Option (2), migrating the shared Sanity schema, is a real, separate decision (affecting 3 other already-live pages) that shouldn't be bundled into shipping one new document under time pressure — TD-010 stays open and unresolved, deliberately, rather than being rushed through as a side effect here. Option (3) matches this project's own proven playbook (`workshops`, `media`, `Ordift Pulse` were all built local-adapter-first, Sanity-adapter-later per `CMS_MIGRATION.md`) and gave the actual required behavior — anchor IDs, a real Document Control table, a real definitions aggregator, a Python publication generator reading the same JSON export — without inventing a parsing layer that would need to be thrown away the moment TD-010 is eventually resolved.
- **Consequences:** OS-LGL-001 is the only document with this richer structure today; `cookies`/`terms`/`booking` remain on the old Sanity/plain-text path unchanged (zero regression, verified live). Adding the next approved document (e.g. OS-LGL-002) means: author `src/lib/legal/documents/os-lgl-00X-<slug>.ts` in the same shape, add one line to `registry.ts`, run `npm run legal:publish:privacy`-equivalent (a new npm script per document, following the same pattern) — no route, layout, or component changes required. When TD-010 is eventually resolved (Sanity portable text), this registry becomes the natural place to add a Sanity-backed `LegalDocument` adapter alongside the in-code one, exactly as `contentRepository` already does for other types — not a rewrite.
- **Alternatives Rejected:** (1) rejected as fragile and directly contrary to TD-010's own stated guidance; (2) rejected as an undiscussed schema migration affecting already-live content, bundled into an unrelated deliverable under time pressure — a decision that deserves its own moment, not a rider on this one.
- **Related Files:** `src/lib/legal/types.ts`, `src/lib/legal/registry.ts`, `src/lib/legal/documents/os-lgl-001-privacy.ts`, `src/lib/legal/definitions.ts`, `src/components/legal/*`, `src/app/legal/[slug]/page.tsx`, `scripts/exportLegalDocumentJson.ts`, `scripts/generateLegalPublication.py`, `TECHNICAL_DEBT_REGISTER.md` (TD-010, TD-020).
- **Review Date:** when TD-010 (Sanity `legalPage.body` → portable text) is scheduled, revisit whether the Enterprise Legal Series should move onto that same Sanity-backed adapter, or whether the code-based source remains the better fit long-term for content this structurally rich and this infrequently changed.

### TDR-012 — Series-wide standing appendices extracted into shared `boilerplate.ts`; applied once at registry level, not duplicated per document

- **Status:** Accepted, implemented
- **Context:** the 2026-08-04 enhancement direction added four appendices (Interpretation & Severability, Accessibility Commitment, Contact Escalation Procedure, Cross-Document Hierarchy) to OS-LGL-001 v1.1, framed explicitly as applying "across every other document yet to be added," not just the Privacy Policy. Later the same day, three more appendices (Jurisdiction-Specific Data Protection Addendum, Government and Law Enforcement Requests, Data Breach Response Summary — see `TECHNICAL_DEBT_REGISTER.md` TD-021) were authorized with the same series-wide framing, immediately followed by the request to integrate OS-LGL-002 (Cookie Policy), the second real document in the series.
- **Problem:** with a second document now arriving, whether to copy all seven appendices' `LegalSection` objects into `os-lgl-002-cookies.ts` (as they had been written directly into `os-lgl-001-privacy.ts`), or extract them once into a shared module every registered document picks up automatically.
- **Options Considered:** (1) duplicate the seven appendix sections into every document file — simplest per-file, but a wording change (or a future Appendix H) would need to be applied N times and could silently drift out of sync across documents; (2) extract into a shared `src/lib/legal/boilerplate.ts` exporting `STANDARD_APPENDICES` and a `withStandardAppendices(doc)` helper, applied once in `registry.ts` when building the exported `documents` map.
- **Decision Made:** (2). `boilerplate.ts` holds the seven appendices; `registry.ts` maps every entry in `rawDocuments` through `withStandardAppendices()` before exposing it via `documents`. Document files themselves (`os-lgl-001-privacy.ts`, `os-lgl-002-cookies.ts`) contain only document-specific sections.
- **Reasoning:** the appendices were explicitly requested as standing, series-wide provisions, not per-document content — treating them as such in code (single source of truth) matches the actual requirement and avoids the exact kind of silent drift a "never invent facts" / accuracy-first project can't tolerate (e.g. two documents disagreeing on the wording of a severability clause because one was hand-copied and edited independently). This also surfaced a real correctness issue with duplication: the original Appendix C (Contact Escalation) referenced "Section 20" by number, which was only correct for Privacy Policy's own Contact section — generalized to "the contact details provided in this document" during extraction so it stays correct regardless of which document's own numbering it's paired with.
- **Consequences:** adding a new document to the series now means authoring only its own sections and adding one line to `registry.ts`'s `rawDocuments` — the seven standing appendices, their numbering (Appendix A–G), and any future Appendix H arrive automatically, already verified against the numbering regex fix below. A related fix was needed alongside this: Cookie Policy introduced the series' first letter-numbered subsections ("A. Essential Cookies" … "F. Future Service Cookies"), which needed the same numeric-style "." suffix as decimal section numbers rather than the em-dash style used for "Appendix A" labels. `LegalSection.tsx`'s `NUMERIC_SECTION` regex was widened from `/^[\d.]+$/` to `/^[\dA-Z.]+$/` (a bare single uppercase letter matches; "Appendix A" does not, since it contains a space and lowercase letters) — and the same widened pattern was applied to all four equivalent copies inside `scripts/generateLegalPublication.py` (`generate_pdf`, `generate_docx`, `generate_html`, `generate_markdown` each had their own independent copy) so the website and all four publication formats stay in agreement. Verified by rendering both regenerated PDFs and loading both pages live: Privacy Policy's Appendices E/F/G and Cookie Policy's "A."–"F." subsection numbering and categories table all render correctly with no letterhead overlap.
- **Alternatives Rejected:** (1) rejected as introducing avoidable drift risk for content the user explicitly framed as standing across the series, and because the "Section 20" bug it would have shipped (silently wrong once copied into a document whose Contact section isn't Section 20) is the kind of error this project's accuracy discipline exists to prevent.
- **Related Files:** `src/lib/legal/boilerplate.ts`, `src/lib/legal/registry.ts`, `src/lib/legal/documents/os-lgl-001-privacy.ts`, `src/lib/legal/documents/os-lgl-002-cookies.ts`, `src/components/legal/LegalSection.tsx`, `scripts/generateLegalPublication.py`, `TECHNICAL_DEBT_REGISTER.md` (TD-021).
- **Review Date:** when OS-LGL-003 (Website Terms) or OS-LGL-004 (Booking Terms) is integrated, confirm the shared appendices still read correctly in context and that no document-specific override mechanism has become necessary (none has been needed for the first two documents).

### TDR-013 — OS-LGL-004's "Part" groupings represented as level-1 wrapper sections, not a schema change

- **Status:** Accepted, implemented
- **Context:** OS-LGL-004 (Master Booking Terms & Conditions) arrived 2026-08-04 as a Production Draft organized into 11 named Parts (A-K), each containing multiple continuously-numbered clauses (1 through 165, running across Part boundaries rather than resetting per Part) — a three-level structure (document → Part → clause) the existing `LegalSection` type doesn't model, since it only has a two-level `level: 1 | 2` field.
- **Problem:** whether to extend `types.ts` with a third level (e.g. `level: 1 | 2 | 3`, or a dedicated `LegalPart` wrapper type) to represent Parts natively, or reuse the existing two-level shape.
- **Options Considered:** (1) add a third level to the type system, touching `LegalSection`, `TableOfContents.tsx`, `LegalSection.tsx`'s numbering logic, and all four Python generator functions; (2) represent each Part as an ordinary level-1 section (`number: "Part A"`, content usually empty or a short intro paragraph) and each of its clauses as an ordinary level-2 section nested immediately after it in the `sections` array — exactly the wrapper/child pattern already established for the shared Appendices in `boilerplate.ts` (`"Appendices"` wrapper + `"Appendix A"`...`"Appendix G"` children).
- **Decision Made:** (2). No changes to `types.ts`, `TableOfContents.tsx`, `LegalSection.tsx`, or `generateLegalPublication.py` were needed — the existing two-level model and `NUMERIC_SECTION` regex (already widened for Cookie Policy's letter subsections, see the Appendices TDR above) handled "Part A" (gets the " —" em-dash suffix, like "Appendix A") and "1"..."165" (gets the "." suffix) correctly with zero code changes.
- **Reasoning:** a third schema level would only ever be exercised by this one document (no other document in the series has 3-tier structure, and none is expected to), so it would add permanent complexity — a new level to reason about in every component and every generator function — to serve a single, currently-unapproved document. The existing wrapper/child pattern was proven correct at smaller scale by the Appendices (7 children under 1 wrapper); this document exercises the identical mechanism at larger scale (up to 22 clauses under one Part). Reusing it kept the change entirely inside one new content file plus a `registry.ts` decision not yet made (this document isn't registered — see `TECHNICAL_DEBT_REGISTER.md` TD-023).
- **Consequences:** the website's sticky sidebar TOC (`TableOfContents.tsx` only lists `level === 1` entries) shows the 11 Part headings plus Contact Information — not all 165 individual clauses, which would be unusable in a sidebar. The PDF/HTML/MD generators list every level in their own table of contents, so those show the full 165-entry breakdown nested under each Part, appropriate for a document this size in print form. Verified by rendering the generated draft PDF (65 pages) and confirming Part K and Contact Information display with correct clause numbering and no letterhead overlap.
- **Alternatives Rejected:** (1) rejected as unjustified schema complexity for a single document, and because it would touch every consumer of `LegalSection` (both website components and all four Python generator functions) for a structural need that a pattern already in production (the Appendices wrapper) already satisfies.
- **Related Files:** `src/lib/legal/documents/os-lgl-004-booking.ts`, `src/lib/legal/boilerplate.ts` (the precedent pattern), `src/components/legal/TableOfContents.tsx`, `TECHNICAL_DEBT_REGISTER.md` (TD-023).
- **Review Date:** if a future document needs a 4th level (e.g. a subsection within a numbered clause), revisit whether the wrapper/child pattern still scales or whether a real schema extension is warranted at that point.

### TDR-014 — `profiles.member_number` is the platform-wide authoritative audit-identity label, resolved from the existing profile_id relationship, not a new stored field
- **Status:** Accepted, implemented
- **Context:** every audit/workflow table already recorded "who performed this" as a `profiles.id` foreign key — `activity_log.actor_user_id`, `workflow_statuses.submitted_by`/`reviewed_by`, `workflow_assignments.assigned_by`/`removed_by` — never a stored name. The *display* layer, however, only ever resolved and showed `profiles.full_name`, across the Admin Activity feed, the Portfolio project detail page's Review Record/History/Assigned Collaborators sections, and (structurally, for any future module built the same way). The business asked, platform-wide, for every "Created By / Reviewed By / Approved By / Published By / Featured By / Archived By / Deleted By / Restored By / Assigned By / Submitted By" surface to record and display against an immutable identifier instead of a display name that can change.
- **Problem:** whether to introduce a new "Staff ID"/"Member ID" concept and column(s) to satisfy this, or find and use whatever the platform already had.
- **Options Considered:** (1) add a dedicated `staff_number`/`audit_id` text column to `activity_log` and every workflow table, snapshotting it at write time; (2) resolve identity at read time from the existing `profile_id` FK against `profiles.member_number` — the append-only-ledger-backed, immutable identifier already built and shipped (migration 0019) as the platform's one people-numbering system, after the earlier `staff_details.staff_number` (migration 0017) was deliberately retired in favor of it for exactly this "one consistent identification system" reason.
- **Decision Made:** (2). No new columns. Built one shared resolver, `resolveActorIdentities()` (`src/lib/portal/actorIdentity.ts`), that batches profile ids to `{fullName, memberNumber, roleLabel, department}` and a `formatActorLabel()` helper producing the "MEMBER-NUMBER — Full Name" display format the business specified. `src/lib/admin/activityLog.ts` and the Portfolio project detail page now resolve through it instead of joining `profiles.full_name` alone.
- **Reasoning:** `profiles.member_number` already is the immutable, human-readable identifier the request describes — assigned once per classification via an append-only ledger (`member_numbers`), changed only on reclassification, with history preserved, never reused. Every audit table's `profile_id`/`*_by` column already points at the right row; storing a second, duplicate identity field on every table would violate the single-source-of-truth principle already established when `staff_number` was retired, and would drift out of sync the moment someone's member_number changed (reclassification) unless every write path remembered to re-snapshot it. Resolving at read time is always current and requires zero schema change.
- **Consequences:** every "…By" display now does one small batched lookup (3 queries regardless of actor count) instead of a single embedded join — a negligible cost against not having to touch 10+ write paths or add migrations. `department` resolves from `staff_details.department`, which migration 0009 already flags as a field an internal `operational_title_id` model was meant to eventually supersede — this decision reads whichever is populated today and isn't blocked on that separate cleanup. Accounts with no assigned member_number yet (freshly created, unclassified) display their name only, never a blank — `formatActorLabel()`'s explicit fallback.
- **Alternatives Rejected:** per-table snapshot columns — rejected as the exact duplicate-identity-field pattern the business explicitly asked to avoid ("align with existing design rather than introducing duplicate identity fields"), and as a correctness risk (stale snapshots on reclassification) with no compensating benefit, since every table already carries the FK needed to resolve the current value live.
- **Related Files:** `src/lib/portal/actorIdentity.ts`, `src/lib/portal/profileCard.ts` (source of the exported `ROLE_LABELS`/`ROLE_DISPLAY_ORDER` this reuses), `src/lib/admin/activityLog.ts`, `src/app/admin/activity/page.tsx`, `src/app/admin/portfolio/[id]/page.tsx`, `src/app/admin/portfolio/actions.ts` (added the missing `portfolio.updated` log call for field-level edits, closing an "Updated By" gap found during this review), `supabase/migrations/0019_member_numbers.sql`.
- **Review Date:** this is now the required pattern for every future module (bookings, HR, models, workshops, finance, legal, CRM, reports) that records who-did-what — a new module inventing its own actor-label logic instead of calling `resolveActorIdentities()`/`formatActorLabel()` should be treated as a regression against this decision, not a fresh design choice.

### TDR-015 — Pulse dedup reference construction uses `_originalId`, not `_id`, under drafts perspective
- **Status:** Accepted, implemented
- **Context:** The Pulse native-draft architecture (commit `9607dc0`, Staging-only) creates discovery-found articles as genuine Sanity draft documents (`drafts.<uuid>`) rather than published-namespace documents. Its deduplication pool (`RECENT_ARTICLES_FOR_DEDUP_QUERY`, `src/lib/pulse/ingestion.ts`) reads via `editorialClient` (`perspective: "drafts"`) so it can see both draft and published existing articles when checking a newly-fetched item against them.
- **Problem:** Controlled Test #5B (a deterministic, fixture-driven discovery run against a synthetic source guaranteed to duplicate an existing genuine draft) failed: `findDuplicate()` correctly matched the item, but the resulting write was rejected by Sanity with "references non-existent document." Root cause: under `perspective: "drafts"`, GROQ's plain `_id` returns the canonicalized/logical identity of a document — the bare id, even when the only document that actually exists is `drafts.<id>`. That canonical id was used verbatim to build `possibleDuplicateOf._ref`, producing a reference to an id that doesn't exist in the dataset.
- **Options Considered:** (1) switch the dedup query to `perspective: "raw"` — rejected: raw perspective treats a draft and its published counterpart (where both exist) as two separate rows, risking double-counted/inconsistent dedup entries, a real, more complex case this project's data doesn't currently exercise but could. (2) Prepend `drafts.` to `duplicate._id` unconditionally at reference-construction time — rejected: would incorrectly prefix references to published-only documents (the common case), breaking a scenario that currently works. (3) Project `_originalId` instead of `_id` in the dedup query.
- **Decision Made:** (3). `RECENT_ARTICLES_FOR_DEDUP_QUERY` now projects `"_id": _originalId` instead of `"_id": _id`. No other code changed — `findDuplicate()`, `dedupPool`, and the `possibleDuplicateOf` construction site are all untouched; only which Sanity system field populates the existing `_id` output key changed.
- **Reasoning:** `_originalId` is Sanity's own field, documented for exactly this purpose (`@sanity/client`'s `SanityDocument._originalId` — populated under a drafts-aware perspective), for retrieving the literal, actually-stored identity of whichever version a perspective query resolved to. It requires no conditional logic and handles both cases uniformly. Verified empirically against the real Staging dataset before implementing: `_originalId` equals `_id` for a published-only document, and correctly returns `drafts.<id>` for a draft-only one.
- **Consequences:** Duplicate references to draft-only articles now persist correctly. The "both a draft and a published version of the same logical document exist" case was reasoned through (perspective resolution prefers the draft, so `_originalId` should follow) but is not empirically verified — no such document currently exists in the Staging dataset (checked dataset-wide, 140 documents, zero matches).
- **Alternatives Rejected:** see Options Considered above — both were live candidates, neither survived scrutiny against the full behavior matrix (published-only / draft-only / both-exist).
- **Empirical verification:** Controlled Test #5B, rerun after the fix (Staging, commit `8e331bd`): server-authoritative `activity_log` record — `fetched: 1, created: 1, flaggedDuplicate: 1, errors: []`. New document `drafts.bcd42ea7-c114-4c8d-9de5-2bac5bb93ee1`, directly verified via raw `sanity documents get` to carry `possibleDuplicateOf._ref === "drafts.32337c6f-e5b6-417c-85e5-3b1eabd32c01"` — the exact literal id of the targeted Test #4 draft. Production dataset confirmed unchanged throughout (`pulseArticle` count steady at 5).
- **Related Files:** `src/lib/pulse/ingestion.ts` (`RECENT_ARTICLES_FOR_DEDUP_QUERY`), `src/sanity/lib/client.ts` (`editorialClient`), `TECHNICAL_DEBT_REGISTER.md` (TD-050).
- **Review Date:** if a `pulseArticle` (or any document read via `editorialClient`) is ever found in both draft and published state simultaneously, confirm `_originalId`'s resolution empirically at that point rather than continuing to rely on reasoned-not-tested behavior.
