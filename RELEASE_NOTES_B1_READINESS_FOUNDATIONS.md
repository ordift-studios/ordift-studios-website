## 2. What B1 contains
* **Professional (My Assignments → the job):** *Pre-assignment readiness* card only for **enrolled** assignments: Ready / Need assistance / Not ready; a service-specific checklist (photography/video/production, design/content/branding, event crew, generic); the seven concern areas (equipment or materials, transport or logistics, location access or permits, schedule or arrival, missing client information, additional crew or technical support, other) and remarks; editable until the start (each edit is a new version); re-confirm prompt after a reschedule; the issue thread and reply box. A readiness chip on the My Assignments cards. Saving does nothing else.
* **Management (Admin → Crew Support → request → "Schedule & readiness"):** Scheduled vs Rescheduled vs Actual, timezone with source, reschedule form with the per-person "who was told" record, timezone override, change history with recorded/outstanding notices, enrol/stop tracking, responsible manager picker (active administrators only, never the assigned professional; Super Admins are the B2 fallback), latest answer and history, 12-hour flag, issues with the actions above and separate shared/internal messages.
* **Overview → Needs attention:** open readiness issues; issues the professional reports sorted (verify); assignments starting soon with no answer; reschedules with someone not yet recorded as told. Test records are excluded.
* **Crew Support → Readiness settings** (management edits, administrators read): intervals; states plainly that nothing is automatic.
* Reuses the existing request / slot / engagement records, role helpers, audit log and uploader-free UI patterns. No new notification system, no parallel scheduling module.

## 3. Security findings
1. **A real access flaw was found by the isolated tests and fixed before any release.** The first version of the readiness read policy decided "is this the assignee?" with a subquery on `engagements`; ordinary staff can see every engagement, so any staff member could have read all readiness rows. Replaced with a `SECURITY DEFINER` assignee check (`private.is_engagement_assignee`), and the real-token RLS test now pins it.
2. Issues, internal notes, follow-ups, schedule history, notices and settings are **administrator-only at the database level**; the professional's view is a server projection of the *shared* events only (mutation-tested: leaking internal notes fails the suite).
3. Nobody can write directly: no INSERT/UPDATE/DELETE grant to `authenticated`; server code has INSERT only on append-only tables (responses, events, schedule changes, notices) and limited UPDATE on enrolment/issues/settings. No DELETE for anyone.
4. **Duplicate protection (database-enforced):** one readiness row per engagement; response version unique; **at most one active issue per assignment** (partial unique index) so repeated or simultaneous answers update the issue instead of raising duplicate escalations; one notice per person per schedule change.
5. **B1 cannot send or auto-enrol even by mistake:** `reminders_enabled` is forced false and `auto_enrol_from` forced null by table constraints; guard tests fail if any B1 module imports an email/notification sender or references files, deliverables, reports, payables or payments.
6. **Separation of duties** is applied consistently with Batch 2: independence from the assigned professional on every management issue action and follow-up assignment, mutation-tested.
7. Rescheduling is management-only (Super Admin / executive admin), atomic in one database function (request + derived engagement dates + history), refuses cancelled/declined/completed requests, and **refuses a change that firmly double-books an assigned professional**; soft clashes only warn.
8. The reschedule function is `SECURITY DEFINER` with a fixed `search_path`, executable by the service role only.
No finding remains open.

## 4. Migration review — `0153_assignment_readiness_and_schedule_integrity.sql`
* **Additive only.** One nullable column (`crew_support_requests.event_timezone`, no backfill, no default) and 7 new empty tables, 3 helper functions, policies and grants. The only `UPDATE` statements are inside `reschedule_assignment()` (request dates and the derived engagement dates), which runs only when management reschedules. No `DROP`, `DELETE`, `TRUNCATE` or change to payments, payables, enquiries or quotations (asserted by a test that reads the SQL).
* **Production compatibility checked read-only today:** every referenced column exists (`engagements.starts_at/ends_at/entity_id[text]`, request/slot/profile columns, `enquiries.payment_country`); helper functions exist; no name collisions; `event_timezone` and `reschedule_assignment` do not exist yet; last applied migration is 0152; `service_role` can read the tables the new code reads and **none of the code touches the three tables Production's `service_role` cannot access**; `authenticated` can use the `private` schema (policy helpers).
* **Risk: low.** Small additive DDL; the nullable column add is metadata-only; no table rewrite; no lock of consequence. **The currently deployed code ignores the new schema, so the migration can go first** and nothing changes for users until the new code is deployed.
* **Order matters the other way too:** deploying this code before the migration would break the new screens (they read the new tables) — hence migration first.
* **Rollback:** `supabase/rollbacks/down_0153.sql`, guarded (refuses if any readiness, response, issue, schedule-change data or timezone override exists). **Tested on the throwaway database in all three ways:** succeeds on an unused database; re-applies cleanly afterwards; refuses once data exists. A code-only problem needs no SQL — promote the previous Vercel deployment.
* **Numbering:** Production is at 0152, so this is 0153. The unapplied payment-policy branch (formerly 0150) will be renumbered to 0154 later; unrelated.

## 6. B2 scheduling — GitHub Actions, verified against GitHub's documentation
* Shortest interval **5 minutes**; **not guaranteed on time** — can be delayed under load (busiest at the start of the hour) and "some queued jobs may be dropped"; scheduled workflows run **only on the default branch** and on its latest commit; in a **public repository they are automatically disabled after 60 days without repository activity** (re-enabled by a write-access user committing a change to the cron line).
* Implications: hourly (offset from :00) is feasible and free for this public repo; dropped/late runs are tolerable **only because B2 will be idempotent and window-based**; the 60-day rule is mitigated by normal commit activity plus a **missed-run alarm** (management Overview flag if no reminder run has been recorded within X hours); the workflow needs the existing cron bearer secret stored as a GitHub secret **by you** (never read or printed by me); fail-closed endpoint (already the Pulse pattern). Vercel Hobby cannot run hourly crons (deployment would fail). **No paid infrastructure is proposed.** Final B2 choice still needs your approval.
